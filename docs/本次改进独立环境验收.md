## 2. 独立环境准备与构建

使用独立机器/虚拟机、PostgreSQL 和 MQTT/Kafka 测试实例。不要复制生产 `forward.env` 或使用生产数据源/输出目标。若使用脱敏配置库副本，首次启动前将 `protocol.enabled` 全部改为 `false`，并替换所有数据源和输出地址、账号、Client ID、Kafka group ID；网络侧禁止测试环境连接生产服务。

准备 Java 21、Maven、Node.js/npm、PostgreSQL 16，以及独立 MQTT 测试 broker；Kafka 流程另用独立 Kafka。已有单元测试不需要真实数据库或 broker，新测试同样仅使用 mock/内存对象，不加载 Spring Boot 应用。

在**独立环境**的仓库根目录运行：

```bash
mvn -f backend/pom.xml test
mvn -f backend/pom.xml -DskipTests package
npm --prefix frontend ci
npm --prefix frontend run build
```

保留 Maven 测试报告、编译输出和前端构建输出；任何失败先反馈，不跳过后继续认为验收通过。`npm run build` 是项目原有 Vite 构建，并非完整 Vue 类型检查。

为部署式测试，将 `backend/target/forward-platform.jar` 复制到测试部署目录的 `backend/forward-platform.jar`，使用该目录专属 `forward.env`。环境文件示例中的密码需要测试人员自行填入：

```bash

FP_DB_SCHEMA=public
FP_DB_USER=fp_test
FP_DB_PASSWORD=<仅测试库密码>
```

运行 `./start-backend.sh`；前端可用测试 nginx 提供构建后的静态文件，或在测试环境运行 Vite 开发服务器。启动脚本必须随新 JAR 一起更新。

### 日志行为和配置

| 项目 | 默认值/行为 |
|---|---|
| JDBC 建连/读取/取消请求超时 | 10 / 60 / 5 秒；通过上面的 `FP_DB_*_TIMEOUT` 覆盖 |
| TCP keepalive | 开启 |
| Hikari 等连接超时 | 保持原值 30 秒 |
| 写库失败后的恢复尝试 | 默认每 30 秒；`forward.log.recovery-interval-ms` |
| 日志队列、批大小和正常刷新间隔 | 保持原值 100000 / 500 / 1000ms |
| 分区维护 | 独立线程启动后执行，每分钟检查；后续每天 00:10 起维护一次，失败后继续重试；恢复写库前补建今天和未来分区 |
| Logback 滚动 | `logs/backend.log`，单文件 50MB，历史保留 7 天，总归档上限 500MB |
| 启动控制台输出 | `logs/console.log`，每次脚本启动覆盖，主要用于早期启动诊断；运行日志不重复输出到控制台 |
| 关闭 | 原日志线程在最多 5 秒的等待窗口内尽力写入；剩余日志放弃，关闭调用方不再执行 JDBC |

日志归档清理按 Logback 的滚动/清理时机执行，总归档上限不包括活动文件。不要用旧命令把控制台重定向到 `backend.log`，让 Logback 独占此文件。现存大日志建议部署前由运维归档；本次不操作正式机器的文件。

超时是各阶段限制，不是整个请求的严格总时限。JDBC URL 中若另有同名驱动参数，需核实最终生效值；不得配置 `socketTimeout=0`。较长数据库查询也可能受读取超时影响，需一并验收历史日志查询。

## 4. 数据库故障与转发稳定性（必须通过）

### 4.1 基线

创建两个协议共享同一个测试 MQTT 数据源，使用不同 Topic 过滤，并绑定测试输出目标。再配置一条使用 `state` 的协议，Worker=1，例如输出递增计数：

```groovy
def value = json.parse(msg)
def count = (state.get('testCount') ?: 0) + 1
state.put('testCount', count)
output([seq: value.seq, count: count])
```

输入使用连续唯一 `seq`，在外部订阅器记录接收时间、序号、输出条数。先用正常流量运行 10 分钟并记录吞吐、延迟、JVM 堆/GC、线程数、broker 连接数、数据库日志行数。吞吐负载先保持在日志正常写入能力内，另设压力场景。

### 4.2 停库、无响应连接和写入拒绝

以下逐项单独执行，每项完成后恢复再进入下一项；不得停止 broker、转发 JVM 或输出订阅器。

1. **停止测试 PostgreSQL**：确认日志进入降级，继续输入 10 分钟，然后恢复数据库。
2. **模拟连接无响应**：对专属测试 PostgreSQL 容器执行 `docker pause <测试数据库容器>`，保持至少 3 分钟，再 `docker unpause <同一容器>`。该操作保留连接但停止数据库回应，可覆盖本次 `Net.poll` 等待场景。容器名必须由测试人员确认，勿针对共享或生产服务。
3. **模拟写盘失败**：在独立库中，通过测试触发器让 `forward_record` 插入抛出 `SQLSTATE 53100`，或使用独立故障代理拒绝写入。不要真的填满宿主机磁盘。故障解除后确认自行恢复。

仅限独立测试库的触发器示例：

```sql
CREATE FUNCTION fp_test_fail_record() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  RAISE EXCEPTION 'test-only simulated disk full' USING ERRCODE = '53100';
END;
$$;
CREATE TRIGGER fp_test_fail_record BEFORE INSERT ON forward_record
FOR EACH ROW EXECUTE FUNCTION fp_test_fail_record();
-- 完成该项后解除故障：
DROP TRIGGER fp_test_fail_record ON forward_record;
DROP FUNCTION fp_test_fail_record();
```

每项预期：

- 已运行协议不重启、不重新订阅；状态聚合计数持续增长，没有因数据库故障引入的序号断档。以外部订阅器为转发证据，不能只看 `out` 计数。
- `/api/status`、`/api/status/overview` 和协议指标继续可读；原版/新版相同负载对比，数据库故障时持续吞吐不低于正常基线的 95%，P99 延迟不高于基线两倍（基线太低时允许 100ms 的绝对增量）。发现超过阈值须保留原始数据分析。
- 数据库请求受超时限制，日志线程不长期停留在同一个失效读取上。连接无响应的典型场景在读取超时后进入 `DEGRADED`；总等待含连接池、建连等阶段，记录实际耗时。
- 降级后两个日志队列回落至 0，丢弃计数增长，JVM 内存不因日志持续累积而增长；配置接口失败不会影响运行中的转发。
- 同类日志写入故障摘要最多每分钟一条，且不含 SQL 参数、完整输入输出或凭据；分区维护故障也为限量摘要。
- 解除故障后不用 `ss -K`、不用重启。连接与分区恢复后进入 `READY`，发送新消息并查询两张表，确认 `logLastSuccessAt` 推进。通常应在 3 分钟内恢复；如分区锁/数据库负载导致超出，记录证据并判为待分析。
- `READY` 表示可接受日志，不等于已有日志落库；必须以最近成功时间和实际查询结果验收。
- 故障期日志允许缺失。恢复后的日志必须是新数据，无无限重试旧批次、无重放业务消息。

### 4.3 长时间离线与跨日恢复

停用测试数据库至少 24 小时，保持稳定消息输入并跨过应用时区的日期边界，每分钟记录外部转发数据、堆内存、GC、线程数、队列和失败计数。

- 全程无数据库原因导致的转发停止、协议重启或 `state` 清零。
- 降级后内存保持稳定，不随离线时长线性上涨；线程数量不持续增加。
- 恢复后分区自动维护并恢复新日志写入。
- 补充执行“缺少当天分区”场景：暂停测试消息，按测试数据管理流程移除测试库当天分区，恢复消息，验证写库失败后后台补建并恢复。不要删任何正式分区，不修改机器系统时钟。

### 4.4 压力、关闭和回归

- 增加测试流量使日志队列达到容量，验证只丢日志、不阻塞主转发；保持上游/输出端未达到自身极限，避免混淆背压原因。
- 正常停机确认原日志线程尽力刷入；无响应连接时停机确认日志组件只等待约 5 秒，之后不再从关闭线程执行第二轮 JDBC。整个进程还包含现有协议排空时间，不应把整个进程退出时长等同于日志组件 5 秒。
- 按测试日志滚动参数生成足量日志，确认滚动、归档清理有效，`console.log` 不重复记录运行日志。
- 使用独立 Kafka 验证接收和发送；验证 HTTP 推送与 MQTT 输出、共享源 Topic 过滤、脚本调试和现有告警提示均正常。
- 数据库离线时重启进程不可用属于既定边界；不要求离线冷启动。数据库健康检查可能显示 DOWN，不能因此认定正在运行的转发已停止。

## 5. 脚本版本验收

| 编号 | 操作 | 预期 |
|---|---|---|
| V1 | 打开脚本页并载入历史版本 | 历史列表默认展开；当前配置、正在运行、编辑中分别标注；载入不改变运行版本 |
| V2 | 修订非当前历史代码与备注 | 保留版本号和创建时间，修订号/更新时间更新；当前转发不重启 |
| V3 | 只修改当前版本备注 | 修订保存，正在运行标识准确；`state`、计数器、broker 连接不重置 |
| V4 | 修改当前代码并保存修订 | 提醒重载和 state 清空；确认后代码生效，版本号不变；只影响该协议 |
| V5 | 修订为不能编译的代码 | 请求失败并显示编译信息；数据库原代码、当前引用和运行状态保留 |
| V6 | 保存为新版本，分别使用有效/无效代码 | 有效代码自动成为当前；无效代码保留为 ERROR 历史版本，原运行版本不变，页面不报成功启用 |
| V7 | 删除当前版本，含直接调用 DELETE | 前端禁用且说明原因，后端返回 409；切换其他有效版本后可删除旧版本 |
| V8 | 删除最高历史版本后再保存新版本 | 版本号继续递增，不复用被删版本号 |
| V9 | 把其他协议的版本 ID 放进当前协议 URL | GET/PUT/DELETE/activate 均拒绝，不读写其他协议脚本 |
| V10 | 两个窗口载入同一版本，先后修订 | 第二个窗口的旧 revision 返回 409，不覆盖先保存的修订 |
| V11 | 有未保存修改时切换载入、切换当前或离开页面 | 提醒放弃修改，取消后内容保留；刷新/关闭窗口触发浏览器未保存提醒 |
| V12 | 模拟脚本保存提交失败 | 原协议不重载；不能出现未提交代码已投入运行 |
| V13 | 提交成功后模拟输出连接异常导致重载失败 | 明确提示“已保存但重载失败”；页面不误报该修订正在运行，修复连接后手动启动并确认 |
| V14 | 停止协议后查看历史版本 | 当前配置仍有标识，所有“正在运行”标识消失；重新进入页面核对 |

新增接口：`PUT /api/protocols/{protocolId}/scripts/{versionId}` 请求为 `code`、`remark`、载入时的 `revision`；删除同一路径用 `DELETE`。版本响应增加 `revision`、`updatedAt`、`current`、`running`。修订覆盖原内容，不保留修订内部的旧文本；需要保留原文本时应“保存为新版本”。

## 6. 分组与排序验收

- 创建 A/B 分组，设置排序码 10/-10，再设相同排序码验证按 ID 升序；空白名称、重复名称、超过 128 字的名称均拒绝。
- 新协议默认未分组、排序码 0；在分组筛选下创建时默认选中该分组。
- 每个协议最多一个分组，“全部”“未分组”和各分组筛选正确；删组后协议归入未分组。
- 设置协议排序码为 -10、0、20 及相同值，协议列表、日志协议下拉、监控大盘按排序码、ID 升序，刷新和重启后保持。
- 正在转发时逐项修改名称、描述、分组、排序、日志保留天数、仅版本备注；验证无协议重连、转发计数重置或 `state` 清零。删组也必须如此。
- 修改真实运行参数（源、Topic、目标、Worker、缓冲大小、采样率）仍按原流程重载。
- API 更新协议时，省略 `groupId` 保持原值，`groupId:null` 移出分组；省略 `sourceTopics` 保持原过滤，显式 `null` 才清空。
- 分组删除/关联并发时，不能产生悬空引用；发生冲突时提示刷新，不能删除协议或停止转发。

分组接口为 `/api/protocol-groups` 的 GET/POST、`/{id}` 的 PUT/DELETE；请求包含 `name`、`sortOrder`。协议接口增加 `groupId` 和 `sortOrder`；排序码为有符号 32 位整数，默认 0。
